# django-htmx-datatable — design and roadmap

Status: draft, 2026-11-15.

## Goal

A reusable Django app that turns a model queryset into a searchable, sortable,
filterable, paginated HTML table, declared once on the server.

It is the successor of [django-ajax-datatable](https://github.com/morlandi/django-ajax-datatable),
without jQuery and datatables.net: the server renders HTML, HTMX swaps it in.

## Decisions

Each decision states the reason, so it can be revisited when the reason no longer holds.

**D1. Standalone core, no django-tables2 / django-filter.**
The value of ajax-datatable is a single declaration (`column_defs`) that drives
rendering, sorting, global search, column filters and queryset optimization.
tables2 + django-filter split that into a `Table`, a `FilterSet` and a view, and
impose their own templates; wrapping them would mean translating between two models.
Pagination and ordering are a few dozen lines; the query engine already exists in ajax-datatable.

**D2. Separate package, private until usable, then open source (MIT) on GitHub.**
Same license as ajax-datatable. No dependency on ColorCraft code: ccshop is a consumer,
not a requirement.
GitLab (`origin`) stays the main repository (issues, MRs, CI); GitHub (`github`
remote) receives `main` and the tags by hand, only when a version is published.
The PyPI name is reserved with a placeholder release 0.0.1 (2026-11-15).
A similar but unrelated name exists: `django-htmx-datatables` (plural, one alpha
release in 2023).

**D3. Server-rendered HTML, no JSON API.**
The view returns either the full page or an HTML fragment. There is no client-side
row model and no JS rendering.

**D4. Client side: HTMX only.**
- One `<form>` wraps the whole table (toolbar, header, filter row, body, pager).
  Every filter input is part of the form, so no `hx-include` lists are needed.
- Sort headers and page links are `<button name="..." value="...">`: HTMX sends the
  value of the button that submitted the form, so no Alpine.js is needed to hold state.
- The page number is never kept in the form: it only travels with the clicked page
  button, so any filter change goes back to page 1 by construction.
- The current ordering is kept in a hidden input.
- Swap strategy: the response replaces only the parts that change (body, pager,
  counters); the header sort indicators and the hidden ordering input are updated
  with `hx-swap-oob`. The filter row is never replaced, so the input being typed
  into keeps focus and caret. No htmx extensions are required.
- Alpine.js is allowed in the consumer's templates (e.g. row selection), never required.

**D5. State lives in the query string.**
Plain GET parameters (names indicative: `q`, `o`, `page`, `len`, `f_<column>`,
`date_from`, `date_to`), optionally prefixed to host several tables on one page.
`hx-replace-url` keeps the browser URL in sync: a table state can be bookmarked,
reloaded and shared. A non-HTMX GET to the same URL renders the full page.
GET only: no POST, no `csrf_exempt`.

**D6. No compatibility layer with django-ajax-datatable.**
The new API is designed on its own terms; the library carries no aliases, adapters
or legacy options to run ajax-datatable code unchanged. Concepts that keep the same
meaning keep a recognizable name (`title`, `visible`, `searchable`, `orderable`,
`choices`, `autofilter`, `lookup_field`, `max_length`, ...), spelled in Python style
(e.g. `css_class`, `initial_search_value` instead of `className`, `initialSearchValue`).
Moving an existing project is a manual procedure, described in a migration guide
(see Roadmap, "Before going public").

**D7. Explicit classes, no dataclasses.**
Columns are plain classes with an explicit `__init__` and keyword arguments: more
verbose, but every attribute and default is visible where it is defined.
Columns are declared only as `Column` objects, not as dicts.

**D8. Unstyled templates, meant to be overridden.**
Minimal semantic markup with stable class names and template blocks; the consuming
project overrides them for its CSS framework.

**D9. Targets: Python >= 3.12, Django >= 5.1, htmx 2.x.**
No compatibility code for older versions.

## Refactoring of the ajax-datatable backend

**R1. One column model.**
ajax-datatable has three overlapping concepts: the column spec dict (normalized on
every request in `initialize()`), `Column` / `ForeignColumn` / `ManyToManyColumn`,
and `ColumnLink` / `PlaceholderColumnLink` / `Order` (DataTables protocol only).
They collapse into one `Column` hierarchy; the protocol classes disappear with D5.

**R2. Validate once, at class definition.**
Column definitions are checked in `__init_subclass__` and errors raise
`ImproperlyConfigured`, instead of a bare `Exception` on every request.
Values that depend on the request (autofilter choices, `get_column_defs(request)`)
are computed lazily, only when the filter row is actually rendered.

**R3. Rendering through hooks and templates, escaped by default.**
Replaces the mix of `render_column_value` formatting, `STRIP_HTML_TAGS`,
post-hoc clipping and `customize_row` mutating a dict:
- `render_<name>(self, obj, value)` on the view for a computed or custom cell;
- default formatting per field type (dates, booleans, choices) in `Column`;
- clipping (`max_length`) done in the template with autoescape on.
  (Today `render_clip_value_as_html` builds HTML with `str.format`, unescaped.)

**R4. Explicit computed columns.**
Replaces `placeholder`, empty column names and the implicit `id` → `pk` rename:
a column either maps to a model field path or is declared computed (not searchable,
not orderable unless a `sort_field` / annotation is given).

**R5. Filters per column, overridable.**
Replaces `build_column_filter` (a type switch in a free function):
- each `Column` subclass builds its own `Q` for a search value;
- `filter_<name>(self, qs, value)` on the view overrides it;
- an invalid date in a date filter is a validation error, not a filter on year 0001;
- the OR separator (`search_values_separator`) is defined for choices too
  (open TODO in ajax-datatable);
- global search is type-aware: a term is applied to a numeric or date column only
  when it parses as a number or a date, instead of failing or emptying the result
  (ajax-datatable issues #88, #131);
- boolean columns get a Yes / No / any select with an exact match (PR #73).

**R6. Stable ordering, explicit NULL placement.**
`pk` is always appended as last ordering key, so rows with equal sort values do not
move between pages. Ordering uses `F(...).asc()/desc()` with a per-column
`nulls_last` option (PR #85, issue #84).

**R7. Cleanups.**
No `eval()` (M2M columns use `getattr`); `logging` instead of `print` and the
`TRACE_*` / `TEST_FILTERS` flags; no `'???'` placeholder values; no Django < 4 branches.

**R8. What is shown, what is sorted and what is searched are three separate things.**
New, not available in ajax-datatable. A column can display one value, sort on other
fields and search in yet others. Example: show "Mario Rossi" in one cell, sort on
`(last_name, first_name)`, search in `first_name` and `last_name` separately:

    Column(
        "customer",
        title=_("Customer"),
        order_by=("customer__last_name", "customer__first_name"),
        search_fields=("customer__first_name", "customer__last_name"),
    )

    def render_customer(self, obj, value):
        return f"{obj.customer.first_name} {obj.customer.last_name}"

- `order_by`: field paths (or annotation names); descending order reverses all of them.
- `search_fields`: field paths (or annotation names) searched with the column's
  `lookup_field`. The search value is split into words; every word must match at
  least one of the fields (same rule as Django admin `search_fields`), so
  "rossi mar" finds "Mario Rossi". The global search uses the same fields.
- Defaults: both are the column's own field path. A computed column without them
  is neither sortable nor searchable (R4).

**R9. Field path resolution.**
One resolver for display, sorting, search and queryset optimization:
- a NULL relation in the middle of a path renders an empty cell, not an error (PR #111);
- reverse relations and `OneToOneRel` are supported (issues #118, #119, #127);
- annotation names are valid paths, so columns can come from `annotate()` in
  `get_initial_queryset()`, including choices/autofilter (issues #129, #132).

## Roadmap

### 0.1 — MVP

1. **Package bootstrap** — `pyproject.toml`, example project, `runtests.py`, GitLab CI.
2. **Column model** — `Column` hierarchy, validation at class definition, field
   path resolver (D6, D7, R1, R2, R4, R7, R9).
3. **Query engine** — global search, column filters, choices/autofilter, FK and M2M
   fields, stable ordering, separate sort/search fields, queryset optimization
   (R5, R6, R8). Port the ajax-datatable test suite as a starting point.
4. **HTMX view, protocol and templates** — single form, sort/page buttons, page
   length, `hx-replace-url`, full vs partial response, rendering hooks, "N of M
   rows" counter (issue #55), configurable search delay (issue #32) (D3, D4, D5,
   D8, R3).
5. **First consumer: ccshop data exchange task list** — a new, read-only page
   (ccshop issue, linked to this project).

### 0.2

- Global date range filter (`latest_by`)
- Row details (expandable row loaded with `hx-get`)
- Footer / totals
- CSV export of the filtered queryset: a plain link carrying the current query
  string, no JS (PR #82, issue #126)
- Show/hide columns (PR #72)
- Multi-column sort (issue #22)
- Multi-select choice filter (issue #105)
- Opt-in "cascading" autofilter: choices taken from the currently filtered rows
  instead of the whole table (issue #90)
- Several tables on one page (parameter prefix)
- Accessibility: `aria-sort`, keyboard navigation of headers and pager
- Second consumer: migrate the ccshop History page (selection, bulk actions, custom cells)

### Before going public

- README with full usage, example project screenshots
- Migration guide from django-ajax-datatable: a manual, step-by-step procedure
  (view class, column declarations, templates, JS removal); no code support (D6)
- Commit author email: decide which address becomes public on GitHub before the
  first push there (changing it later means rewriting history)
- Private links: replace `gitlab.brainstorm.it` URLs in `pyproject.toml`
  (`[project.urls]`), README and docs with the GitHub ones
- Issue references: `Refs #N` / `Closes #N` in commit messages point to GitLab
  issues; on GitHub they link to unrelated GitHub issues (harmless, but misleading)
- External contributions: PRs opened on GitHub are brought back to GitLab by hand
  (`git fetch github pull/N/head:<branch>`); if they become frequent, consider
  making GitHub the main repository
- Create the GitHub repository, push `main` and the tags
  (`git push github main --tags`), publish the release on PyPI

### Later

- Export to PDF of the filtered queryset, same link mechanism as CSV; the PDF
  renderer becomes an optional dependency (extra), not a requirement of the package

### Not planned for now

- Inline cell editing (issue #116)
- Grouped headers with colspan/rowspan (issue #113)
- JSONField keys as columns (issue #83)
